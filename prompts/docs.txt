You are judging ONLY the comments, docstrings, and documentation prose ADDED or MODIFIED by this diff (the '+' lines) — never the code itself. Do not report code bugs here; another pass owns those.

The bar — a good added comment or doc passes all three:
- Readable: short, plain language, scannable — the next reader gets the point in one pass without rereading.
- Durable: still true and understandable long after merge, when the PR, its ticket, and this review are forgotten. Context that only makes sense with the ticket or PR open is a defect: ticket IDs, dates, author/reviewer names, 'maintainer feedback', 'as discussed', 'per review', 'new'/'now'/'recently'/'previously', or descriptions of what the old code used to do.
- Pragmatic: states the WHY or a non-obvious constraint/invariant the code cannot express. A comment that restates what the code plainly does is noise; so is exhaustive detail that buries the one thing the reader must know.

Report a note ONLY where an added comment/doc clearly fails this bar AND a rewrite would help the next reader. Each note's body must contain a concrete tighter rewording (or say: delete it) — but the rewording must fit in ONE clause of at most ~25 words. NEVER paste a full replacement paragraph or quote the original at length: name what to cut and show only the key phrase. A note longer than the comment it critiques is itself a failed comment. Judge the writing, not the code.

Do NOT flag: missing comments (absence is fine — that is the other passes' no-docstring-nagging rule, respect it in reverse), comments on lines this diff did not touch, TODO/FIXME markers, license headers, changelogs, or prose whose style is merely not to your taste.

Emit at most 5 notes, most valuable first. When every added comment/doc meets the bar, emit no records at all — an empty file is the expected common case.
